How to plan cloud infrastructure for production AI

The GPU is one decision. The application is the system you need to get right.

Stratum Editorial · September 22, 2026 · 7 min read

In this guide

Service requirementsGPU memoryKubernetesStorage & databasesRecovery & migrationMonthly costsLaunch checklist
The quick answer

Plan production AI infrastructure around the complete request path. Size GPU memory for the model and concurrent requests, benchmark latency and throughput, then account for data access, orchestration, resilience and operating cost. Validate the design with representative traffic before committing to capacity.

A model that runs successfully in a notebook is not yet a production service. Once users arrive, prompts compete for memory, data retrieval adds latency and traffic becomes uneven. The question changes from whether the model runs to whether the application can meet its response targets consistently.

A useful infrastructure plan connects those requirements to measurable capacity. Here is a practical sequence for building one.

1. Define the service before the server

Start with the experience the application must deliver. An interactive assistant needs a different response profile from an overnight document-processing job. Record input and output lengths, expected concurrency and acceptable wait times.

For interactive language-model services, track time to first token and the interval between generated tokens. Measure percentile latency as well as averages, because slow requests often reveal problems that a single mean conceals.

  • Traffic: What is the expected request rate, and how large are bursts?
  • Data: Where must application data, logs and backups reside?
  • Recovery: How much downtime and data loss can the business tolerate?
  • Operations: Who handles upgrades, incidents and capacity changes?

2. Budget memory beyond model weights

GPU memory holds more than the model. It also supports the KV cache, activations, temporary buffers and the inference runtime. Longer contexts and more concurrent sequences can significantly increase memory demand.

As a rough illustration, 8 billion parameters stored at two bytes each require about 16 GB in decimal units for weights alone. That calculation excludes runtime overhead and request state. It is not a recommended GPU size.

Quantization can reduce weight memory, but the quality and performance effects depend on the model, method and hardware. Compare realistic outputs and latency before treating a lower-precision configuration as equivalent.

The vLLM optimization guide explains how memory and scheduling choices affect serving capacity. Use it as a starting point, then benchmark your own configuration.

3. Choose orchestration for an operating need

A small service can start on a virtual machine. Kubernetes becomes useful when teams need repeatable deployments, multiple services, resource scheduling and a consistent operating model across workloads.

It also introduces responsibilities. Plan worker capacity, networking, persistent storage, observability and version upgrades. Managed control planes reduce one part of that work, but do not remove responsibility for application behavior or data protection.

For mixed workloads, separate CPU and GPU node pools where appropriate. Define resource requests, scheduling constraints and scaling signals deliberately. Adding replicas only helps when capacity is available and the application can use it.

The Kubernetes overview is useful for understanding what the platform provides and what remains outside its scope.

4. Design the data path alongside compute

A fast GPU can still wait on model downloads, document retrieval or database queries. Keep frequently accessed data close to the serving tier and measure the latency of each dependency.

Do not choose database capacity from CPU usage alone. Inspect query execution, memory pressure, storage waits and connection counts. More compute will not automatically fix an inefficient query or a slow storage path.

5. Make failure and migration testable

Define a recovery time objective for restoring service and a recovery point objective for acceptable data loss. Then test whether your backup, replication and failover design can meet them. A backup job marked successful is not evidence of a successful restore.

For migrations, inventory dependencies before moving data. Rehearse with a representative environment, validate consistency and document the conditions that trigger rollback. Keep the original environment available until the destination passes the agreed checks.

6. Model the full monthly cost

Start with resource quantity, rate and billable duration. Add persistent storage, database capacity, backups, outbound transfer, load balancing and any support or software charges. Record the assumptions so estimates can be reviewed later.

A part-time GPU job may run for fewer hours than the database supporting it. Stopping compute does not necessarily stop storage charges. Model each resource on its own billing basis, and confirm the provider’s actual terms.

The Stratum cost calculator separates the major resource categories and lets you change the unit rates. Its default rates are illustrative, so replace them with a provider quote before using the output for procurement.

Your pre-production checklist

  • Benchmark representative prompts, output lengths and concurrent requests.
  • Record latency, throughput, GPU memory usage and failure rates.
  • Test data access and database behavior under the same load.
  • Restore a backup and rehearse a rollback.
  • Assign an owner for alerts, upgrades and capacity changes.
  • Compare the measured architecture with the monthly budget.

The best configuration is the one that meets your service requirements with enough operating headroom and a cost you can explain. Start small, measure carefully and expand from evidence.
